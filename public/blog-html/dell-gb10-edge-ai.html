SECTION 01

GB10이 대체 뭔가 — 한 칩에 들어간 원룸

What GB10 actually is — a studio apartment on one chip

GB10 그레이스 블랙웰 슈퍼칩은 NVIDIA가 만든 단일 칩으로, 두 종류의 프로세서를 한 몸에 붙였습니다. 블랙웰(Blackwell)급 GPU와 그레이스(Grace)급 ARM CPU를 NVLink-C2C(칩과 칩을 직결하는 초고속 통로)로 묶고, 둘이 하나의 메모리 풀(128GB)을 공유합니다. Dell은 이걸 담아 Pro Max with GB10이라는 데스크용 박스로 출시했고, NVIDIA의 DGX Spark와 사실상 같은 설계입니다.

The GB10 Grace Blackwell superchip is a single NVIDIA chip that fuses two kinds of processor into one body: a Blackwell-class GPU and a Grace-class Arm CPU, joined by NVLink-C2C (a chip-to-chip express lane) and sharing one 128 GB pool of memory. Dell ships it as the desk-side Pro Max with GB10, essentially the same design as NVIDIA's DGX Spark.

비유 · 원룸 vs 따로 사는 부부Analogy · a studio vs a long-distance couple

보통 PC는 CPU와 GPU가 따로 사는 부부 같습니다. 각자 자기 메모리(RAM / VRAM)를 갖고, 데이터를 주고받을 때마다 PCIe 버스라는 택배로 짐을 부칩니다 — 느리고 번거롭죠. GB10은 둘이 같은 원룸(통합 메모리)에 사는 격이에요. 같은 데이터를 양쪽이 곧바로 보니, "이 텐서가 지금 CPU 쪽이야 GPU 쪽이야?"를 고민할 필요가 없습니다.

In a normal PC, the CPU and GPU are like a long-distance couple: each keeps its own memory (RAM vs VRAM) and ships data back and forth by courier — the PCIe bus — which is slow and fiddly. GB10 is more like the two of them sharing one studio apartment (unified memory). Both see the same data directly, so you never have to ask “is this tensor on the CPU side or the GPU side right now?”

Remember just this: memory is large at 128 GB (a big model fits whole), but bandwidth is slower than a desktop GPU's (so it loses raw-speed drag races), and it makes up for that with FP4 ultra-low-precision math and unified memory. Those three lines are the entire personality of the GB10.

SECTION 03

통합 코히런트 메모리 — 마찰의 제거

Unified coherent memory — removing friction

통합 메모리(unified memory)는 CPU와 GPU가 같은 128GB를 공유한다는 뜻이고, 코히런트(coherent)는 한쪽이 값을 바꾸면 다른 쪽이 즉시 같은 값을 본다는 뜻입니다(일관성 보장). 디스크리트(분리형) VRAM에 익숙한 개발자가 가장 많이 버리는 시간이 바로 "RAM ↔ VRAM 복사와 동기화"인데, GB10은 그 단계를 통째로 없앱니다.

Unified memory means the CPU and GPU share the same 128 GB, and coherent means when one side changes a value the other instantly sees it (consistency is guaranteed). The single biggest time-sink for developers used to discrete VRAM is copying and syncing between RAM and VRAM — GB10 deletes that step entirely.

왜 중요한가Why it matters

링 버퍼를 새로 짜고, 포인터 소유권 스케줄을 맞추고… 이런 '배관 작업'이 사라집니다. 그래서 디스크리트 VRAM(예: 24GB)에 갇혀 실험을 줄이던 사람이, 여기선 RAM과 VRAM을 저울질하지 않고 더 야심 찬 실험을 끝까지 돌립니다. 용량(128GB)이 크니 모델·리트리버·임베딩을 동시에 상주시킬 수 있는 게 핵심.

No more inventing a ring buffer or negotiating a pointer's custody schedule — that “plumbing” goes away. People who shrank their experiments to fit discrete VRAM (say 24 GB) suddenly finish more ambitious ones because they're not balancing RAM against VRAM. With 128 GB, you can keep the model, the retriever, and the embedder all resident at once — that's the point.

SECTION 04

FP4의 마법 — 느린 메모리를 빠르게 느끼게

The FP4 trick — making slow memory feel fast

AI 모델은 수많은 숫자(가중치)로 이뤄지는데, 그 숫자를 몇 비트로 표현하느냐가 정밀도(precision)입니다. FP16/FP8/FP4… 비트가 적을수록 메모리·연산이 가벼워지죠. FP4는 단 4비트 — 블랙웰의 트랜스포머 엔진이 이 FP4를 일급 시민으로 하드웨어 가속합니다. (참고: 이건 제가 이전 글에서 다룬 양자화(Quantization)의 최신 갈래입니다.)

An AI model is a sea of numbers (weights), and how many bits you use to write each one is its precision. FP16 → FP8 → FP4: fewer bits means lighter memory and math. FP4 is just 4 bits, and Blackwell's Transformer Engine accelerates it as a first-class citizen in hardware. (This is the cutting edge of quantization, which I covered in an earlier post.)

핵심 수치 · NVFP4Key number · NVFP4

NVIDIA의 NVFP4 양자화는 2단계 스케일링과 마이크로텐서 단위 보정으로, 많은 체크포인트에서 FP8 대비 정확도 손실을 약 1%p 이내로 유지합니다. 여기에 스페큘러티브 디코딩(작은 모델이 먼저 빠르게 초안을 내고 큰 모델이 검증)을 얹으면, 대역폭이 느린 LPDDR이라도 채팅·코딩이 체감상 빠르게 느껴집니다. 마케팅이 아니라 수학입니다.

NVIDIA's NVFP4 quantization, with two-level scaling and per-microtensor calibration, keeps accuracy on many checkpoints within ~1 percentage point of FP8. Stack speculative decoding on top (a small model drafts quickly, the big one verifies) and even slow LPDDR feels snappy for chat and coding. That's not marketing — it's the math that makes this class of box feel fast.

실전 함의: 약 110GB 메모리 예산이면 1,200억 파라미터급 모델을 FP4로 양자화해 상주시키고도, 임베딩 모델과 리트리버를 위한 여유까지 남습니다. "용량이 모자라 절벽에서 떨어지는" 일이 없다는 뜻이죠.

The practical upshot: a roughly 110 GB memory budget lets you keep a 120-billion-class model resident at FP4 and still leave headroom for an embedding model and a retriever — no falling off a capacity cliff.

SECTION 05

스프린터 vs 십종경기 선수

Sprinter vs decathlete

"RTX 4090 두 장이면 더 빠르다"는 비교를 자주 봅니다. 맞습니다 — 단일 작업의 원본 속도(FP8)에선 데스크탑 GPU가 이깁니다. 하지만 그건 틀린 질문에 답하는 경우가 많아요.

You'll often see “two RTX 4090s are faster.” True — for raw speed (FP8) on a single task, a desktop GPU wins. But that's often answering the wrong question.

비유 · 한 종목 vs 열 종목Analogy · one event vs ten

4090 두 장은 합쳐 48GB VRAM의 단거리 스프린터입니다 — 하나의 좁은 루프에서 눈부시죠. GB10은 십종경기 선수예요. 한 종목은 느려도, 세 종목을 동시에 뜁니다 — 메모리에 다 들어가니까. 멀티모달·멀티에이전트에서 통합 메모리가 사주는 초능력이 바로 이겁니다.

Two 4090s are a sprinter with 48 GB of VRAM between them — brilliant in one tight loop. GB10 is a decathlete: slower on a single event, but it runs three events at once because they all fit in memory. That's the superpower unified memory buys you for multimodal and multi-agent setups.

NVIDIA 데모의 정석 예시: GPT-OSS 1,200억 파라미터를 감독(supervisor)으로 두고, 코드 모델과 비전-언어 모델을 동시에 메모리에 올린 멀티에이전트 구성. 질문 하나 답하려고 모델을 메모리에 넣었다 뺐다 하지 않습니다 — 오케스트라 전체가 무대에 올라 있죠.

The canonical NVIDIA demo: GPT-OSS at 120B as a supervisor, flanked by a code model and a vision-language model, all resident at once in a multi-agent setup. You don't swap models in and out to answer one question — the whole orchestra is on stage.

SECTION 06

세 가지 실증 — "실제로 뭔가를 한다"

Three real jobs — “it actually does something”

① 큰 모델을 로컬에서 (LLM + RAG + 도구)

① A big model, locally (LLM + RAG + tools)

Ollama 같은 도구를 CUDA로 컴파일하고 TensorRT-LLM에 링크하면 블랙웰의 FP4 경로를 탑니다. 120B급 양자화 모델 + 적당한 컨텍스트 + RAG(문서 검색 결합)까지 한 박스에서. 코딩·문서 Q&A에 "실제로 쓸 만한" 수준이 됩니다.

Compile a tool like Ollama with CUDA and link it against TensorRT-LLM to ride Blackwell's FP4 path. A 120B-class quant + a reasonable context window + RAG (retrieval over your documents), all in one box — into the “I can actually use this” tier for coding and document Q&A.

② 강화학습 (Tempest 게임 에이전트)

② Reinforcement learning (a Tempest game agent)

강화학습(RL)은 에이전트가 시행착오로 "어떤 행동이 보상으로 이어지는가"를 배우는 방식입니다. 게임 프레임에서 핵심 지표를 뽑아 GB10으로 보내면, GB10이 리플레이 버퍼(과거 경험 저장소)에 쌓고 초당 수백 번 무작위로 꺼내 학습합니다. NumPy와 PyTorch만 설치하면 CUDA가 바로 잡히고, 서버 구동과 학습을 같은 박스에서 처리 — 스레드리퍼 타워 두 대를 손바닥 상자가 대체합니다. 가장 빠르진 않아도 "충분히 빠릅니다".

Reinforcement learning (RL) is how an agent learns, by trial and error, “which actions lead to reward.” Extract key metrics from game frames, send them to the GB10, and it piles them into a replay buffer (a store of past experience), sampling thousands of frames hundreds of times per second to train. Install just NumPy and PyTorch and CUDA is right there; it runs the server and the training on the same box — a palm-sized unit replacing two Threadripper towers. Not the fastest, but fast enough.

③ 집 앞 영상 분석 (클라우드 없이)

RTSP = IP 카메라 영상 스트리밍 표준 프로토콜. DeepStream = 영상 디코딩~추론을 GPU에서 끝까지 처리하는 NVIDIA 파이프라인(CPU 낭비 X). YOLO = 한 번에 사물 위치(바운딩 박스)를 찾는 경량 객체탐지 모델. 임베딩(embedding) = 차량의 외형을 숫자 벡터로 요약한 '지문'. 이 지문을 NVMe의 벡터 인덱스에 우리 집 차들로 미리 채워두고, 들어온 차의 지문이 기존과 동떨어지면(OOD, out-of-distribution) = '처음 보는 차'로 판단. n프레임 연속 지속될 때만 알림 → 오탐 억제. 디코딩→탐지→임베딩→판단 전 과정이 박스를 떠나지 않습니다.

RTSP = the standard protocol for streaming IP-camera video. DeepStream = NVIDIA's pipeline that decodes and infers end-to-end on the GPU (no CPU waste). YOLO = a lightweight detector that finds object locations (bounding boxes) in one pass. Embedding = a numeric “fingerprint” summarizing a car's appearance. Prime a vector index on NVMe with your household's cars; if a new car's fingerprint is out-of-distribution (OOD) versus that gallery, it's “new.” Require persistence across n frames to suppress false alarms. The whole loop — decode → detect → embed → decide — never leaves the box.

SECTION 07

스케일아웃 — 두 대로 베이비 클러스터

Scaling out — a baby cluster from two boxes

뒷면의 QSFP 포트는 장식이 아닙니다. 내장 ConnectX-7 네트워크 카드는 포트당 100Gbps를 내고, 두 대를 묶으면 NCCL(여러 GPU가 협력해 한 모델을 나눠 처리하게 해주는 NVIDIA 통신 라이브러리)로 작은 클러스터처럼 돌릴 수 있습니다.

The QSFP cages on the back aren't decoration. The built-in ConnectX-7 NIC does 100 Gbit/s per port, and wiring two boxes together lets you run NCCL (NVIDIA's library that lets multiple GPUs cooperate on one model) like a baby cluster.

현실적 기대치Realistic expectations

한 칩 내부의 NVLink만큼은 아닙니다. 하지만 텐서 병렬(큰 디코더를 쪼개 분담)이나 MoE(전문가 혼합 모델의 라우팅)에는 충분한 네트워크 패브릭이에요. 공식 수치로 따뜻한 상태에서 풀 듀플렉스 130–150Gbps, 박스가 완전히 바쁘면 그 절반 수준. "썬더볼트 케이블 두 개"식 꼼수가 아니라 실제 패브릭입니다. 한 대는 큰 디코더, 다른 한 대(사이드카)에 임베딩·리트리버를 고정하면 도구를 늘려도 메모리 압박이 평탄해집니다.

It's not an on-chip NVLink domain. But it's a fabric good enough for tensor-parallel inference (splitting a big decoder across both) or MoE (mixture-of-experts routing). Reference figures: 130–150 Gbit/s full-duplex on a warm system, about half when the box is saturated. Not a “two Thunderbolt cables” hack — a real fabric. Put the big decoder on one node and pin the embedder/retriever on the other (a side-car) to keep memory pressure flat as you add tools.

SECTION 08

소프트웨어 스택 — 마찰 없는 경험

The software stack — frictionless

설치는 리눅스 관리자 코스프레가 아니라 대시보드 접속 → VS Code 연결 → 작업 시작에 가깝습니다. OS는 우분투 기반 DGX OS, 툴체인은 CUDA · TensorRT · Triton · PyTorch · vLLM 그대로. "ARM이라 걱정?" — 커널 드라이버를 크로스 컴파일하는 게 아니라, 어차피 다른 곳에도 배포할 CUDA/Python/C++를 작성할 뿐이라 대부분 그냥 동작합니다.

Setup is less Linux-sysadmin cosplay, more open the dashboard → connect VS Code → get to work. The OS is Ubuntu-based DGX OS; the toolchain is the toolchain — CUDA · TensorRT · Triton · PyTorch · vLLM. Worried about Arm? You're not cross-compiling kernel drivers — you're writing the same CUDA/Python/C++ you'd deploy elsewhere, so most of it just works.

가장 깊은 가치 · 이식성The deepest value · portability

책상 위 이 작은 박스에서 짠 코드가 데이터센터의 B200 랙까지 그대로(1:1) 올라갑니다. 더 큰 블랙웰로 갈 때 바뀌는 건 "쓸 수 있는 전력"과 "NCCL 링이 보는 GPU 수"뿐. 지금 GB10에서 배운 게 그대로 미래의 큰 장비에 적용됩니다.

Code you write on this desk-side box carries one-to-one up to a B200 rack in a data center. Moving to bigger Blackwell only changes how much power you can spend and how many GPUs your NCCL ring sees. What you learn on a GB10 today applies later, unchanged.

SECTION 09

산업 현장 활용 분석 — 어디에 진짜 쓸까

Industrial use — where it really fits (my analysis)

세 데모를 산업 언어로 번역하면, GB10이 빛나는 자리가 분명해집니다. 제 관점(온프렘 GenAI를 만드는 사람)에서 다섯 가지 케이스로 정리합니다.

Translate those three demos into industry language and the spots where GB10 shines get clear. From my vantage point (someone who ships on-prem GenAI), five cases.

① 데이터 거주성이 필수인 온프렘 LLM·RAG

① On-prem LLM/RAG where data residency is mandatory

현장Field

금융·의료·제조·공공처럼 데이터를 외부로 못 내보내는 도메인. 사내 문서·계약서·도면 위에 RAG를 얹은 프라이빗 어시스턴트를 한 박스 안에서 완결합니다(검색→생성 전 과정 온프렘). 데모 ①·③이 정확히 이 모양 — "클라우드로 안 보낸다"가 요구사항인 곳에 딱 맞습니다.

Finance, healthcare, manufacturing, public sector — domains where data can't leave the building. A private assistant with RAG over internal docs, contracts and drawings, self-contained in one box (retrieval → generation all on-prem). Demos ① and ③ are exactly this shape — a perfect fit where “no cloud” is the requirement.

② 공장·물류·리테일의 엣지 멀티모달 비전

② Edge multimodal vision for factories, logistics, retail

현장Field

'집 앞 차량 감지'를 그대로 산업으로 옮기면 — 불량 검출, 안전모/출입 통제, 재고·진열 인식, 차량/팰릿 추적입니다. 현장(엣지)에서 디코딩~판단을 끝내니 지연(latency)·대역폭·프라이버시 문제를 동시에 해결하고, 카메라가 늘면 "스트림과 NIC만 더"하면 됩니다. CUDA 그대로라 창고 규모 다중 카메라로 확장도 매끈.

Move “driveway detection” into industry and it becomes defect inspection, PPE/access control, inventory & shelf recognition, vehicle/pallet tracking. Doing decode-to-decision at the edge solves latency, bandwidth and privacy at once; adding cameras is “more streams, more NIC.” Same CUDA, so scaling to a warehouse-scale multi-camera system is smooth.

③ PoC → 프로덕션 이식성, 그리고 플릿 배포

③ PoC → production portability, and fleet deployment

현장Field

책상에서 만든 PoC가 같은 CUDA 스택으로 데이터센터 B200까지 직행합니다. "로컬에서 되던 게 프로덕션에서 안 되는" 흔한 함정을 줄이죠. 게다가 Dell은 이걸 표준 SKU로 — 서비스·예비 부품·관리 가능한 이미지로 — 제공하니, PoC가 "현장 10만 대"로 커질 때 플릿 장비처럼 다룰 수 있습니다. 이게 단순 미니PC와의 결정적 차이.

A PoC built at your desk goes straight to a B200 in the data center on the same CUDA stack, cutting the classic “worked locally, broke in prod” trap. And Dell ships it as a standard SKU — with service, spares and a manageable image — so when a PoC grows to “100,000 units in the field,” you treat them like fleet devices. That's the decisive gap versus a generic mini-PC.

④ 멀티에이전트 워크스테이션 (동시 상주)

④ A multi-agent workstation (everything resident)

현장Field

코드베이스를 아는 LLM + 도면·PDF를 이해하는 리트리버 + 소형 영상 분석 + 학습 루프를 한 번에 요구하는 워크플로우. 십종경기 선수의 특기(동시 상주)가 그대로 생산성으로 — 엔지니어 1인용 'AI 연구실'을 책상 위에 둘 수 있습니다.

Workflows that need an LLM that knows your codebase + a retriever that understands drawings/PDFs + small-scale video analytics + a training loop, all at once. The decathlete's specialty (keeping it all resident) turns directly into productivity — a one-engineer “AI lab” on a desk.

⑤ 비용·전력 — "미터기 불안" 없는 상시 가동

⑤ Cost & power — always-on without meter anxiety

현장Field

~230W는 1년 내내 켜둬도 전기료가 '수백' 단위지 '네 자리' 후회가 아닙니다. 본체 ~$3–4K. 클라우드 GPU 시간당 과금에 비하면, 상시 추론·학습 워크로드를 고정비로 돌릴 때 매력적이죠. 결론: 정말 필요할 때만 클라우드로 가고, 기본은 로컬.

~230 W means leaving it on all year is a “few hundred” bill, not four-figure regret. ~$3–4K up front. Against hourly cloud-GPU billing, it's compelling for always-on inference/training as a fixed cost. The takeaway: go cloud only when you truly must; default to local.

언제 쓰지 말아야 하나 (냉정하게)

When NOT to use it (soberly)

한계 직시Know the limits

ⓐ 단일 작업의 원본 FP8/BF16 최대 처리량이 전부라면 → 데스크탑 4090급이 낫습니다. ⓑ 워크로드가 이미지 생성 한 가지뿐이라면 → 통합 메모리·듀얼 QSFP가 필요 없습니다(과한 투자). ⓒ $2,000대 AMD AI 미니PC나 통합 메모리 큰 M시리즈 맥도 FP8 추론·개발 경험은 훌륭하지만, 블랙웰 FP4 일급 지원·듀얼 100GbE·동일 CUDA 온램프는 없습니다 — GB10이 진짜 파는 건 이 '정렬(alignment)'입니다.

ⓐ If raw FP8/BF16 throughput on one task is all you need → a desktop 4090-class card is better. ⓑ If your only workload is image generation → you don't need coherent memory or dual QSFP (overkill). ⓒ A ~$2K AMD AI mini-PC or a big-unified-memory M-series Mac give lovely FP8 inference and dev experience, but not Blackwell FP4 as a first-class citizen, dual 100GbE, or the same CUDA on-ramp — that alignment is what GB10 actually sells.
